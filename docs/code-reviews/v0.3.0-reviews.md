# Architecture and design review — v0.3.0

Date: 2026-10-09
Scope: all five packages (`agentbot`, `agent-control-backend`, `agent-control-frontend`, `agentbot-computer-agent`, `agentbot-windows-companion`), the sandbox image, deployment scripts, and documentation under `docs/`.
Evidence: source and documentation read in full or sampled; Python suite executed (`pytest -q`, 354 passed in 90 s, Docker-marked tests not run). No code or documents were modified as part of this review.

Related documents: [architecture-blueprint.md](../architecture-blueprint.md), [agent-control-implementation-status.md](../003-agent-control-implementation-status.md), [agent-control-backend-features-plan.md](../018-agent-control-backend-features-plan.md).

---

## 1. Overall verdict

This is a well-reasoned design with unusually strong security and durability thinking for a project this young, but the implementation has outrun its own architecture. The blueprint (dated 2026-10-07) labels B2–B11 as "Planned"; the status document says B3–B11, Autopilot, Windows companions, and Azure compute are all done. That delta — roughly 21k lines of Python, 12k lines of TypeScript, and 108 uncommitted files on top of three commits named "MVP" — is the main risk. The core abstractions are good; the control plane that grew around them is becoming a monolith held together by convention.

### Snapshot metrics

- Python source (non-test): ~21,200 lines. Python tests: ~7,400 lines. TypeScript (src + e2e): ~12,100 lines.
- Backend return-type annotations: 66 of 509 function definitions. Kernel package: fully annotated.
- Raw `db.execute(...)` call sites in the backend: ~470 across 22 modules.
- Inline (function-scoped) imports in the backend: 52. `hasattr(...)` capability probes: 25. Cross-module access to `_private` members: 67.
- Largest modules: `cloud.py` 1,579 lines / 59 functions; `WorkspaceCenter.tsx` 1,850 lines.
- No `.github/`, no pre-commit config, no ruff/mypy/pyright configuration in the repository.
- Git: 3 commits; 108 files staged or modified in the working tree.

## 2. What is done well

- **Layering and dependency direction.** `agentbot` (kernel) has zero imports from `agentbot_control`; the frontend depends only on the wire contract. `ISandboxClient` and `IAgentFrameworkAdapter` in `packages/agentbot/src/agentbot/interfaces.py` are small and genuinely framework-blind. Two adapter shapes (adapter-owned loop in `ClaudeAgentAdapter`, SDK-owned loop with a queue bridge in `MicrosoftAgentAdapter`) prove the abstraction works.
- **Fail-closed security posture.** Approval timeout resolves to deny; foreign resources return 404 rather than 403; Origin guard on unsafe HTTP methods and on WebSocket upgrade; JSON-only request bodies; no wildcard CORS with credentials; Fernet encryption at rest; secret redaction before event persistence; a pure `desktop_plan.py` validated on the host and executed in the container; `cap_drop ALL`, `no-new-privileges`, no mounts, no Docker socket. The threat model in blueprint §10 is explicit and mostly matches the code.
- **Durable runtime semantics.** State change and its event are appended in one `BEGIN IMMEDIATE` transaction; receipts make commands idempotent; `interrupted` / `outcome_unknown` after restart with no automatic retry; `GuardedSandbox.drain()` so a run is marked `cancelled` only after in-flight side effects settle; an OS-level process lock refuses a second control process. These are the right distributed-systems instincts.
- **Testing shape.** Every model boundary is a protocol with a scripted fake; the frontend reducer is pure and exhaustively tested; BDD acceptance runs against Azurite; Playwright covers four viewport sizes. 354 tests in 90 s without Docker is a healthy inner loop.
- **Documentation volume and "honesty rules."** MUST-tagged invariants and the UI rule "never fabricate state" are rare and valuable.

## 3. Weaknesses

### 3.1 `Runtime` has become a service locator / god object

In `packages/agent-control-backend/src/agentbot_control/runtime.py`, `Runtime.__init__` constructs fourteen subsystems (`Computers`, `Files`, `Control`, `Terminals`, `Lifecycle`, `Workspaces`, `WindowsComputers`, `CloudComputers`, `Autopilot`, `Groups`, `Toolkit`, `ToolLibraries`, `Routines`, …), each of which takes `runtime` back as a constructor argument. Consequences observed in code:

- 52 inline imports exist to break the resulting import cycles.
- `kernel.sandboxes` is monkey-patched twice with `__getattr__`-delegating routers (`ProviderRouter` in `windows.py`, `CloudProviderRouter` in `cloud.py`), and `kernel.registry.register_framework("ufo", …)` is called from the control plane.
- Capabilities are grafted onto other objects at runtime: `store.approvals`, `store.capabilities`, `store.workspace_service`, `store.tool_libraries`; and on the streamer: `tool_access`, `sandbox_guard`, `action_handler`, `authorize`, `allowed_policy_id`, `request_intent`.
- 25 `hasattr(...)` capability probes replace explicit interfaces.
- 67 cross-module accesses to `_private` members (`catalog._fernet`, `store._event`, `store._workspace`).

The kernel's "framework-blind" invariant still holds, but only because nobody has broken it yet; nothing structural enforces it.

### 3.2 Typing discipline collapsed at the package boundary

`agentbot` is fully annotated; `agentbot_control` has return types on 66 of 509 functions. There is no ruff, mypy, or pyright configuration, no pre-commit hook, and no `.github/` workflow — nothing runs the 354 tests automatically.

### 3.3 Data access is diffuse

Roughly 470 raw `db.execute(...)` calls across 22 modules, each opening its own `store.transaction()`. `app.py` reads `user_preferences` JSON inline inside route handlers. The single SQLite connection (`check_same_thread=False`, guarded by an `RLock`) is called synchronously from async handlers, so every write blocks the event loop. This is fine for one user; it is the scaling ceiling, and the process lock is the tell.

### 3.4 Kernel purity is eroding

`packages/agentbot/src/agentbot/workflows/blob_orders.py` is an Azure Blob daily-orders ETL and `agentbot/tools/blob.py` wraps it; `MicrosoftAgentAdapter` imports it directly. Use-case code now lives inside the "framework-agnostic kernel." `agentbot` also hard-depends on FastAPI and uvicorn because the raw gateway ships in the same distribution as the library.

### 3.5 Giant modules

`cloud.py` is 1,579 lines / 59 functions. `WorkspaceCenter.tsx` is 1,850 lines and defines its own local types that duplicate API shapes. The Vite dev log shows repeated "Could not Fast Refresh" warnings caused by non-component exports in component files (`CloudComputerSettings.tsx`, `WindowsComputerSettings.tsx`, `ToolLibraryPicker.tsx`).

### 3.6 Two parallel wire protocols in the UI

v1 frames (`session/reduce.ts`, one WebSocket per bot) and v2 envelopes (`session/v2.ts`) both live; the backend keeps a legacy facade (`serve_legacy`). This doubles the surface over which the "never fabricate state" rule must be enforced.

### 3.7 Acknowledged security gaps now carry higher stakes

Egress from containers is unrestricted; Chromium runs with `--no-sandbox`; there is no login or registration rate limiting; the Fernet key is `SHA-256(AGENTBOT_SECRET)` with no key version. These were tolerable when a human approved every action. With Autopilot (unattended decisions), routines, webhook triggers, and Azure VMs, prompt-injection-to-exfiltration is the realistic attack and unrestricted egress is its path.

### 3.8 Docs and history no longer describe the system

`README.md` still links `docs/architecture.md` as the primary design document and never mentions the `ufo` framework, cloud computers, or Autopilot. Blueprint status tags are stale. Three commits ("MVP", "MVP", "windows companion") provide no archaeology. The blueprint's own clause "where this document and code disagree, code wins" is already load-bearing.

## 4. Top improvements, in priority order

1. **Make the composition root explicit.** Replace the `Runtime(self)` back-reference pattern with constructor-injected, typed dependencies: a `Protocol` per service (`SandboxManager` with optional capability sub-protocols instead of `hasattr`, `ApprovalStore`, `WorkspaceAccess`, …). Stop grafting attributes onto `store` and the streamer. *Why:* the safety invariants (framework-blind kernel, tenant-blind sandbox) are currently enforced by habit; this makes them enforceable by import-linting and type checking, and it unblocks every other refactor.

2. **Introduce a repository layer and move SQLite off the event loop.** One module per aggregate (runs, approvals, computers, workspaces, routines, …) owning its SQL; a single writer executed via `asyncio.to_thread` or a dedicated writer task. *Why:* 470 scattered SQL sites turn every schema change into a grep; synchronous writes under `asyncio` will surface as latency as soon as two users run bots concurrently. It is also the only credible path to Postgres.

3. **Add CI and static gates before more code lands.** ruff + pyright (strict on `agentbot`, gradual on `agentbot_control`); `tsc --noEmit` + eslint; pytest, vitest, Playwright; a Docker-capable job for `pytest -m docker` that fails if tests skip (the blueprint already states this). *Why:* the suite is good; nothing guarantees it runs, and the typing gap only widens.

4. **Reconcile docs with code and commit in reviewable slices.** Update blueprint status tags and README entry points; split the 108-file working tree into per-milestone pull requests; promote the "Key design decisions" table in the blueprint into ADRs. *Why:* a 56 KB blueprint that is wrong about what exists is worse than a short one that is right — an agent or a new engineer will build against it.

5. **Evict use-case code from the kernel and split the distribution.** Move `workflows/blob_orders.py` and `tools/blob.py` into the control plane's tool-libraries package (or a dedicated `plugins` package); split `agentbot` into a dependency-light core and a separate gateway distribution. *Why:* blueprint invariant 1 and dependency hygiene; the kernel should be installable without FastAPI or an ETL script.

6. **Close egress before unattended modes are used for real.** Per-session Docker network with a proxy allowlist; block `169.254.169.254` and RFC 1918 ranges; apply the same rules to Azure VMs via NSG. Add login/registration rate limiting. *Why:* Autopilot removes the human gate that currently compensates for open egress.

7. **Decompose the two giants.** `cloud.py` → config, bindings, reconciler, routes. `WorkspaceCenter.tsx` → one component per tab. Generate TypeScript API types from the backend (FastAPI OpenAPI → `openapi-typescript`) instead of hand-typing them in components. *Why:* these two files are where most future defects will hide, and duplicated types are how the UI starts fabricating state.

8. **Retire v1 in the UI once v2 is complete.** Keep `serve_legacy` for the raw gateway only. *Why:* one reducer, one reconnection story, one place to enforce the honesty rules.

9. **Observability.** Emit the planned metrics (active runs, oldest pending approval, event lag, termination failures) and structured JSON logs correlated by `run_id` / `bot_id`. *Why:* with routines and webhooks, failures will occur when nobody is watching the UI.

10. **Key management.** HKDF-derived key with a `key_version` column and a re-encrypt rotation command. *Why:* "rotation makes all stored keys unreadable" is acceptable for a demo, not for a multi-user deployment.

---

## 5. Structural opinion

The design is trying to be two things at once: a small, auditable kernel with a reference control plane, and a full SaaS-style workspace product (sharing, groups, routines, skills, connectors, Autopilot, three compute providers). Both are legitimate goals, but the second needs the modularity, data layer, CI, and egress controls listed above before it is safe to expand further. Recommended: freeze feature work for one iteration and spend it on items 1–4; the remaining items then become mechanical rather than risky.
